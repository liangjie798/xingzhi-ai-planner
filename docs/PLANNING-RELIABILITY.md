# 排程可靠性与组织者工作区

## 旅游规则排程

`tourism-scheduler.ts` 同时处理规则兜底与模型推荐候选，模型不能绕过程序约束。每次停留包含游览/用餐与排队，站点之间另计交通、休息。餐饮使用午餐/晚餐窗口；普通景区在营业未知时采用9:00–17:00的保守假设，明确列为待确认。名称与近距离位置共同用于去重，避免场馆别名重复。

逐小时预报按完整停留窗口读取。户外候选对降水、空气质量和热风险计入排序；达到当前产品的保守筛选阈值时不予安排。这些阈值是产品筛选规则，不是医学判断、气象预警或安全认证。数据不完整会标记待复核，不能生成已验证天气结论。

先使用坐标估算选择候选；随后对不超过 8 个入选候选调用高德距离测量 API 生成全对驾车时长矩阵，用于第二轮排序；最后对相邻站点按直线距离选择步行（≤1.5 公里）、骑行（≤4 公里，老人/儿童/敏感人群/低强度行程除外）、公交（≤12 公里，同城）或驾车接口，分别加 5、8、12、15 分钟缓冲。公交接口失败改查驾车，矩阵不可用时保留坐标估算。排程并不保证全局最短路径，不包括首站前与末站后的酒店通勤，不等于实时导航或已预约车辆。

高德 `opentime_today` 仅适用于查询当日，不将当日营业时间外推为未来日期开放承诺。不规则营业文字、未来日期、节假日和团体接待均保留待确认。来源接口说明：[POI服务](https://developer.amap.com/api/webservice/guide/api/newpoisearch)、[路径规划](https://lbs.amap.com/api/webservice/guide/api/direction)。

删除地点前保存方案快照；删点后重新计算保留地点的时间、天气、估算交通与休息，并更新地图、时间图、规划书。该次修改不重新查询路况，关联地点费用移除、公共费用保留。旧版路线需重新分析才能使用完整排程编辑。

## 推荐理由

`tourism-reason.ts` 逐站生成推荐理由，只使用排程已算出的地点类型、商圈、当日位置、距离、用餐时段与停留窗口天气，不额外推断热度、评分或营业结论。内置候选文案仅在出行月份、到访钟点与路线方向一致时复用，出现季节、夜游或预约等不匹配说法时退回中性描述。模型给出的定性理由需通过数字、平台热度与钟点校验；距离、路况来源与用餐衔接由程序补齐，未通过校验时同样使用程序描述。

## 外部数据源与降级

- 高德仍是地点与路线主源：POI 2.0 文本/周边检索、行政区、步行/骑行/公交/驾车路径与距离测量矩阵。相邻站按直线距离选模式：≤1.5 公里步行（+5 分钟）、≤4 公里骑行（+8 分钟，老人/儿童/敏感人群/低强度除外）、≤12 公里同城公交（+12 分钟）、更远驾车（+15 分钟）；公交失败改查驾车，矩阵只用于候选排序，最终相邻站由对应方式校准并明确标注来源。
- 天气主源为 Open-Meteo。后端配置 `QWEATHER_API_KEY` 后，气象请求失败会切换到和风天气；备用只返回其实际覆盖的小时，当天更早时段直接省略，不补造数据；空气质量仍来自 Open-Meteo，取不到时沿用当日缓存或明确失败。`QWEATHER_HOURS` 可设为 24、72 或 168，对应和风天气的计费档位。
- 维基导游（Wikivoyage）的观光、饮食与抵达段落作为路线参考进入检索摘要和证据页，保留原文链接并标注 CC BY-SA；请求超时或页面不存在时不阻塞主流程。中国大陆服务器通常无法直连 Wikimedia，可通过 `WIKIVOYAGE_API_URL` 指向可达镜像或代理，否则该来源标记为不可用。
- OpenStreetMap 仅作为可选补充：配置 `OSM_OVERPASS_URL` 后才检索城市周边公园，坐标由 WGS-84 转为 GCJ-02，并标注 ODbL 来源；公共实例不可达时自动跳过。
- 百度地图为交叉校验源：配置 `BAIDU_MAP_AK`（可选 `BAIDU_MAP_SK` 做 SN 签名）后核对站点坐标。主源已找到且偏差超过 800 米时保留高德坐标并在轨迹与证据中标注；主源缺失时仅在 1.5 公里内采用百度坐标。百度使用 BD-09，服务端统一转 GCJ-02。
- 以上新增依赖全部通过环境变量启用，未配置时不会发起请求，也不会改变现有降级行为。

## 证据展示

首要指标改为推荐地点资料关联覆盖率。关联资料不等于营业、预约和接待已验证。官方说明、数据接口和未核验全文的检索摘要分别展示，未取得资料的地点明确列出。搜索入口过滤旅行社排名、跟团推广等内容；旅游路线只保留能关联实际站点的检索摘要，不用通用SEO文章充数。

## 用户信息与场景深化

环境评分风险类别与具体身份分开保存：大学生仍按成年人风险类别计算，但 `audienceDescription` 保存大学生身份，用于地点偏好、确认卡和规划书。人均预算、器材数量与每组人数单独记录；“每组5人”不会覆盖总人数。

- 研学：行前问题、场馆主题任务、证据记录、小组分享和教师评价。
- 运动会：项目排程、同日场地/负责人/参赛编号冲突、结果与异常记录。
- 体育课：按人数、每组规模和器材数计算练习站及轮次，缺器材资料时不假定充足。
- 社区：报名/到场与容量核对任务、需求分区、志愿者分工、参与反馈记录。
- 户外训练：训练目标、基础确认、补给/撤离和天气变化处理。距离、爬升、通行未知时不编造路线参数。
- 旅游：完整时间排程、地点编辑、交通来源与预算明细。

## 六个工作区与数据

分析台、环境地图、执行方案、执行管理、资料库、活动档案分别承担输入、空间分析、文档、项目费用、人工核对及版本复盘。

工作区数据使用原有账户隔离的 `/api/v1/conversation-memory` 保存；访客按会话保留，注册用户按账户保留。项目和费用按城市、活动与日期范围隔离。当前提供组织者账户内的分工记录，不提供跨账户实时协同、通知发送、在线支付或自动场馆预约。参与者说明可下载，默认不含名单。

每次完成分析自动保留版本，最多4份，可载入、比较条件、填写复盘并归档。资料最多60条，项目及费用各100条；服务端记忆总量上限仍为100万字符。资料的“已人工核对”由组织者选择，当前不自动等价为Agent已读取全文。执行记录和费用不是场馆容量或预算可行性的认证。

## 出发地与交通比较

对话分别保存 `originCity`、交通目的地 `journeyDestination` 和交通日期 `departureDate`，避免交通比较覆盖已生成的目的地活动日期。连续表达“榆林市榆阳区明天出发2个人”按完整行政区提取；完整路径查询失败时，通过高德父级行政区的子区县核对归属，同名多结果不再直接选择第一项。

交通查询使用自建航司官网只读工具，首批启用5家已通过独立浏览器会话验证的适配器；不将展示价当成最终含税最低价。火车票通过12306公开查询获取车次、席别与票价；两类结果分别加载，不能以不完整票价比较火车与航班总费用。详见[票价服务配置](TICKET-SEARCH.md)。

实时报价不作为长期记忆复用，切换城市或日期后旧结果不显示。旧版手工记录保留在原记忆结构中，但不再参与票价比较。“资料库”现为“资料收藏”，用于个人链接和核对笔记，不是 Agent 知识库。
